# No-JavaScript proof of concept

## Approach and critique

The page is static HTML built by Eleventy. It contains a native form and a snapshot of up to 25 responses. The API remains a JavaScript service: a normal browser form receives a bodyless 303 to the site with a status fragment; JSON clients retain JSON responses. JavaScript progressively refreshes the cloud and enhances submission. A 303 is the standard way to direct the user agent to a retrieval after a POST ([HTTP semantics](https://httpwg.org/specs/rfc9110.html#status.303)); Eleventy supports asynchronous data files ([documentation](https://www.11ty.dev/docs/data-js/)).

The snapshot is only as current as the latest successful build. Posts and deletions do not update the no-JavaScript page until a rebuild, including after a successful form submission. This is especially important for moderation: deleted content may remain in an already published snapshot or cached page. A fast removal requirement needs an explicitly tested rebuild/invalidation process or a different rendering approach. A build fails if the API is unavailable or returns invalid data; the previous deployment remains available, but releases depend on the API. This is a deliberate tradeoff, not live server rendering.

The native POST requires the API changes in the sibling checkout; until those changes are deployed, the proof of concept cannot complete a native submission against production. A failure before the API handler runs may show a platform error instead of a friendly redirect. Browser Back may recover input, but this is browser-dependent. Fragment status messages are linkable and cannot prove a submission occurred. The API's current read-modify-write of a single KV value can lose concurrent writes and can resurrect a deleted response; the static snapshot does not address that existing storage limitation.

Set `SCOTTIS_API_URL` at build time to a staging or local responses endpoint; otherwise it defaults to the production API. The form, snapshot and enhancement use the same endpoint. Do not put credentials in this public URL. Configure the corresponding frontend origin in the API's allowed origins for isolated testing.

## Proposed rebuild trigger

Use a Vercel Deploy Hook for the frontend production branch. After the API confirms a successful storage write or deletion, send a POST to the configured hook from server-side background work, as with the existing notifications. Do not trigger it for duplicates, validation failures, or unsuccessful deletions. Keep the URL in a server-side environment variable: possession permits deployments. Missing configuration should disable the trigger for local and preview environments; never expose the URL to the browser or logs. A hook acknowledgment means a deployment was queued, not that the new snapshot is live. See [Vercel Deploy Hooks](https://vercel.com/docs/deploy-hooks).

The trigger is best-effort unless durable retries are added: a failed request, failed build, deployment limit, or stale upstream read can leave the snapshot unchanged. Log a controlled failure without the URL and monitor both hook failures and failed deployments; document a manual rebuild and verification path, especially for removals. Verify that the first build after a deletion actually reads the updated data; KV propagation and concurrent writes can undermine that assumption. Vercel cancels earlier deployments for repeated requests to the same hook, but build/deployment limits still apply ([limits](https://vercel.com/docs/limits)). Measure expected submission volume and build latency before triggering a deployment for every successful write. A periodic or batched rebuild is an alternative if volume becomes significant; neither guarantees immediate deletion.

Before using the hook, verify branch targeting and whether the deployed branch contains only reviewed changes. Each hook invocation deploys the configured branch's code as well as refreshing data, so it must not accidentally publish unrelated code. Test with a separate non-production hook and isolated data. Do not create or invoke a production hook as part of this proof of concept.

## Implementation and migration plan

1. Agree on acceptable maximum snapshot age and removal time. Evaluate the proposed deploy-hook trigger against those needs, expected build frequency, and concurrent changes. If it cannot meet them, choose dynamic HTML rendering or another explicitly approved approach.
2. In a non-production environment, test the API's JSON contract and native form success, duplicate, invalid input and storage failure. Check missing and disallowed origins, redirect targets, Back behavior and pre-handler failures. Test with scripts disabled in more than one browser. Use disposable isolated data, not public submissions.
3. Test the frontend build against the same isolated endpoint: escaping, ordering and empty state, API failure and timeout, GET/POST race, stale snapshot messaging, failed refresh retention, pagination and repeat submissions. Verify that CSS/JS and no-JavaScript pages are correct at narrow widths and with assistive technology.
4. Decide how to address concurrent storage writes and moderation before relying on immediate deletion. Review API changes separately, including any existing delete behavior, notification behavior and deployment environment variables. Avoid leaking preview responses into production.
5. For a release, review the commits and deployment. Verify API compatibility and rollback strategy, then coordinate frontend and API ordering so neither depends on a missing contract. Confirm both production aliases, static HTML and JSON requests after deployment without creating public test posts. Monitor build failures and ensure a documented path to rebuild after removals.

The dependency audit currently reports a moderate development-only ESLint dependency advisory; production dependency audit is clean. Recheck the lockfile and Node runtime compatibility before any release.
